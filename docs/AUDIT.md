# 0.4.0 灵枢记忆同步域审计（增补）

审计日期：2026-11-21。对象：新增的灵枢记忆域（`lib/lingshu.js`、`lib/lingshu-bridge.py`、协议/计划器/策略/引擎接线）。0.3.0 记录保留在下方，未被覆盖。

## 结论

| 问题 | 处置 |
|---|---|
| 裸写 `.md` 是否可用 | 不可用。实测：改写既有文件后索引签名与目录指纹都不变，`get()` 见新值而 `search` 见旧值；新增文件对运行中的进程完全不可见。故写入只走 `MdCGSecure.add()`。 |
| 是否绕过灵枢写入闸 | 不绕过。桥不设置 `MDCG_WRITE_GATE`、不传 `reviewed_by`；`knowledge/structural/self/anchor` 在默认 `enforce` 下被拒时返回 `memory-needs-review`，插件不重试、不降档。真实宿主验证：知识层节点应用后 B 侧无文件落盘。 |
| 本机易变字段会不会被远端冲掉 | 不会。`add()` 继承未提供字段；桥显式保留本机 `edges`；`sensitivity` 仅对新节点上送；canonical 投影剔除 30 个本机/派生键。真实测试：覆写后 `edges`、`sensitivity`、`session`、`access_count` 保持本机值。 |
| 密级与凭据外泄 | 密级上限默认 `internal`，加密节点（`<!-- mdcg-enc:v1:`）直接跳过；导出前复用灵枢 `data/policy.json` 的 `forbidden` 正则拦截，命中即跳过。审计/提案只保留 key、层与哈希。 |
| 路径与文件类型 | 仅 `<root>/<layer>/**/*.md`，深度 ≤3；拒绝软链、非普通文件、硬链（`nlink≠1`）、超长、根外路径；节点 id 走 `^[A-Za-z0-9_.@-]{1,128}$`。 |
| 子进程边界 | 桥以 `spawn(python, [bridge])` 运行，stdin 单行 JSON、stdout 带 `RESULT_JSON:` 前缀解析，stderr 截断；120 s 超时后 SIGKILL 并报 `lingshu-bridge-timeout`；不读用户 shell 配置、不拼 shell 字符串。 |
| 批准与自动应用 | `memoryWrite` 不进 `AUTO_ACTIONS`，操作固定 `risk:'high'`；批准仍绑定 planHash、策略哈希、来源修订与本机基线。 |
| 删除与快照 | 对端缺席 = 不删除；快照不导出记忆节点，导入也无法注入。 |

## 已知边界

- 桥依赖本机能 import 到灵枢的 Python 包；找不到时域只读、不提供写入，不会退回裸文件通道。
- `knowledge/structural` 的同步可用性取决于灵枢侧复核通道；插件不代做复核。
- 本版按批起 Python 进程，单批成本约 0.3–1 s（47 节点索引）；未实现常驻 worker。
- 未做跨 WAN、Windows/macOS 与灵枢未来版本的兼容矩阵。

# 0.3.0 安全与业务流程审计

审计日期：2026-11-20。对象为此仓库的插件源码和实际打包内容；宿主依据 DSH 0.2.2-rc.3 随包文档、类型与实现核对。本记录不会把隔离实例验收当成使用者当前 profile 已安装的证据。0.3.0 未做新的外部渗透测试，本轮验证是回归、静态审查和单机实测；0.2.0 的外部验收记录保留在文末，并明确标注未重跑。

## 发现与修复

0.2.0 的 93 项单测通过，但覆盖不了本轮的域删除和设置页重写。本轮重新追踪入口、策略、建议、计划、批准和实际写入，确认并修复了以下问题。

### 安全边界

- 原状态目录和 credentials 固定地址被所有 profile 共用。现按 home/profile/目录生成独立作用域；损坏状态拒绝启动，禁止静默重置。
- 原配置只按键名脱敏，未知 schema 可把秘密放在普通字段中。现配置默认不外发，必须明确纳入资源并列出非秘密字段路径；入站/出站均重新投影。
- 原 `localOnly`/方向主要作用在计划上，不能覆盖提案、初始发布与快照外发。现全部外发入口复用相同本机范围，配置按真实所属 bundle 保护。
- 记忆同步域已在 0.3.0 整体移除：`lib/memory.js`、`memWrite` 能力、记忆资源类型、记忆计划/提案/快照字段与适配器读写全部删除。`RESOURCE_KINDS` 只剩 `plugin`、`pluginConfig`，`ACTIONS` 去掉 `memWrite`；远端 `kind:'memory'` 由 `validateResourceRecord` 以 `unsupported resource kind` 拒绝。本插件不再读取、写入或导出任何记忆/人格文件，0.2.0 记录的记忆路径、owner、锁与备份边界随整域移除而失效（不是放宽，而是不再存在）。
- 原快照仅验证整体摘要与数组类型，重算普通摘要可夹带无效资源。现复用在线资源类型、地址、实际内容哈希与大小校验，明确区分未可信来源和本机密钥验证的 HMAC；快照只接受插件与配置两类资源。
- 原 SSH 远端 curl 只有路径而没有完整地址；shell 展开后 bearer 还可能出现在远端 curl argv。现使用系统 `ssh -W` 直接 TCP forwarding，生成完整 HTTP 请求，不启动远端 shell/curl；严格校验 host key，超时终止子进程，限制响应字节。该传输在本轮未改动。
- 配对身份、独立 bearer 哈希与提案 HMAC 绑定具体设备；信任不传播，撤权后该设备的凭据不再被接受。原暂停未覆盖对端读取/提案，也没有撤权入口；现暂停阻断新同步入口，撤权拒绝后续认证并清除待用批准/队列。
- 原 agent 检查可能返回建议片段或资源正文。现在工具返回元数据投影，建议只发送插件元数据（key、enabled、kind）；用户界面的配置值也不混入计划显示。
- 设置页保存时固定写 `default:'deny'`，`mode` 随自动应用写 `managed`/`selective`。旧版 `default:'allow'` 下清空 `include` 等于全同步的语义不再产生；旧状态加载时自动迁移并落盘（删除记忆字段、`pendingSnapshot.expectedMemory`、`caps.memWrite` 和带 `adapterId/relativePath` 的旧建议），旧状态不会因多余字段校验失败。迁移不改写旧策略的 `default`；白名单 `default:'deny'` 在设置页下一次保存时写入，升级后应先确认范围。
- 本地 API 仍复用 DSH connection 认证，要求 POST/JSON 并检查浏览器同源信息；远端 API 单独用配对凭据认证，请求/响应有大小限制与超时，不跟随携带凭据的重定向。

### 流程正确性

- 修正 `check(all)` 漏掉插件和配置，以及 UI 导入快照把对象误传给字符串解析器的问题。
- 两类计划分开管理批准；策略、来源或本机基线改变会失效旧批准，部分批准不能绕过安装依赖启用插件。
- 安装先停用落地；升级保持真实启用状态。成功单项先持久化，失败可以在正确基线下重试，升级失败后的启用重试不再误判基线。
- 配置写入核实唯一活动条目与真实 bundle 归属，锁内以当前完整配置为基底；不能写错相同 ID 的条目或覆盖本机秘密/非受控字段。
- 对等角色此前只在直接函数测试里“可用”。现在真实角色可交换状态、排队/领取/确认提案；冲突决定到接受时才发布，过时提案需要重新检查。加测还复现并修复了监听端反向提案“已接受但无本机应用计划”的断路：目标选择按因果关系合并本机已接受状态和对端状态，保留无关资源；单测验证下一轮不回滚，真实 HTTP 验证接受后能批准并落盘，无需额外发布绕路。
- 单方本机改动保留为差异；并发改动进入冲突，人工选择生成新计划再批准。`ai-suggest` 不再伪装成模型选择中心版本。
- 建议改为只扫插件：系统插件给 `localOnly`、已停用给 `skip`、已启用给 `sync`、已在 `include` 里的不再建议；`suggest` 只写建议，`adopt` 必须由用户触发才写 `include`/`localOnly` 并清空待用批准。模型只收到插件元数据。
- 设置页按白名单工作流重写：进入页面自动读取插件清单，勾选即保存（没有保存按钮，文本规则约 600 毫秒防抖）；一个插件都不勾时明确提示不会同步；建议卡可一键全部纳入；计划卡勾选后一次点击完成批准和应用；范围 JSON 在本地生成/读取，不走网络。界面回归共 11 项，覆盖这些路径、发布/提案分支和点对点邀请。
- 设置页重写时曾漏掉中心发布入口，中心还会显示注定失败的「发给对方」。现按角色分支：中心或点对点监听端显示「发布本机改动」，成员显示「看差异」「发给对方」；补 1 项 UI 回归验证两侧按钮和实际请求。
- 点对点监听端的邀请按钮曾被错误地按 `role==='peer'` 一律禁用，导致第二端拿不到邀请码。现改为真正的 `peerLimit`（已有 `center` 或已有已连接对端才禁用），补 1 项 UI 回归。
- 审计、资源和队列均有上限。已决提案可通过本机私有备份后归档释放队列；不会删除待审内容，也不会把满队列伪装成成功。

### 冗余与可维护性

- 合并两类资源计划器和共用策略/校验路径，减少各域分支漂移。
- 合并审计实现，修复滚动窗口后序号重复；移除第二份无界 JSONL 副本写入。
- 删除 `lib/memory.js` 及记忆专用测试；清除未接线的帮助代码和 locale 中重复的 UI 字典，保留 DSH 导出的显示元数据。`npm run check` 现在检查 15 个运行 JavaScript 文件。
- 运行包仅提交原生 JavaScript；React 由宿主提供，测试 renderer 只作为开发依赖。新增字段、入口和发布白名单均有检查。
- 设置页改用宿主真实主题令牌并保留降级值，避免宿主未提供这些变量时解析为空、卡片边框和底色不渲染。

## 适用边界

点对点支持一对设备，多设备使用中心；不存在已验证的多跳网状同步。自动应用不覆盖安装、升级或冲突；记忆同步域已移除。没有真实收费模型调用、两台物理主机 WAN、防火墙/代理组合、Windows/macOS 桌面端的全矩阵验证。

本机同账户任意改代码的攻击者不在进程内隔离保证内。字段启发式不是完整秘密检测，用户明确选入的普通字段仍需自己确认可分享。没有全局回滚、撤销外部副作用或远程抹除已获副本的保证。
